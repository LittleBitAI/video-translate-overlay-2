# PC–Android sync over shared local network via Google account identity (no server), plus download and mobile transcription speedups — PRs #6, #7, #8 merged

The user asked for full PC–mobile synchronization tied to a Google account, and reported two problems: audio downloads are too slow, and mobile transcription is too slow, including how to split audio without cutting speech mid-utterance. After rejecting Google Drive appdata, a hosted sync service with FCM, and Firebase Auth + Firestore, the user chose server-less sync. Google sign-in establishes that two devices belong to the same account, and the running PC syncs directly with the phone on a shared local network. Three specs followed: PR #6 (sync, 14 completion criteria), PR #7 (audio download speed, 10 criteria) and PR #8 (mobile transcription speed and chunk boundaries, 12 criteria), all merged with 0 remaining P2.

## Decisions

- Sync scope covers the library (completed translations, subtitles, video info, playlists) and playback position
- Deleting an item, once confirmed, deletes it on every device, including devices that were offline
- Preserve transcription quality: no model downgrade and no paid transcription to gain speed (rejected: Model downgrades or paid transcription)
- Measure a real-device baseline first, then set speed acceptance targets — Splitting or other changes should not be assumed to help before the dominant delay is identified
- No hosted server or cloud database. Google account sign-in is used only to verify both devices belong to the same account; the user's running PC syncs directly with their phone — User wants sync built on Google account linking alone, without deploying GCP or a server; PC is assumed to be running when cross-syncing (rejected: Google Drive appdata storage; hosted sync service with FCM push; Firebase Auth + Cloud Firestore with WorkManager polling)
- Sync works on a shared local network: the phone discovers the PC through local network discovery (Android NSD), then the devices authenticate the same Google account over an encrypted connection and exchange changed records — With no intermediary, devices on different networks (e.g. a phone on mobile data) may not be reachable (rejected: Worldwide/cross-network connectivity)
- Any Google account may use sync; each account accesses only its own records
- Sync exchanges individual records into each device's local SQLite library rather than overwriting the database — Overwriting the database would let simultaneous changes erase each other (rejected: Whole-database overwrite)
- Sync uses app-level Google authentication, not YouTube cookies — The existing Google connection is only YouTube login (rejected: Inspecting YouTube login cookies)

## Facts

- The PC app is a Rust/Tauri app; the native app deliberately exposes no network command server, and the sync interface must keep existing app commands and API keys inaccessible to peers (unverified)
- Before this work, translated subtitles were saved locally in SQLite and reused when a video was reopened; the Google connection was YouTube sign-in only, with no library sync (unverified)
- The transcription splitter detects sound by volume, groups nearby activity, and cuts long stretches at the quietest point between roughly 20 and 30 seconds. Chunks are at most 30 s, forced cuts have no overlap, and no textual context is carried between chunks (unverified)
- Proposed chunk-boundary design: prefer a sustained pause found by speech detection (VAD); if speech continues, use about 1 s of overlap and reconcile the overlap by timestamps and matching words; keep chunk offsets on the original video timeline; persist the boundary plan; give translation neighbouring text as context (unverified)
- On first use, the 'downloading' stage also downloads the Android speech model (about 60 MB) (unverified)
- Direct files download over a single stream and HLS segments download sequentially; a failed audio download restarts from zero; YouTube format selection prefers AAC and then higher bitrate (unverified)
- The Android build already uses a smaller model, greedy decoding, and up to 4 threads (unverified)
- Sync waits while the PC is unavailable or the network blocks device communication; local copies stay usable (unverified)
- PR #6 (LAN sync, Windows–Android) merged at round 4 with 14 completion criteria passed; PR #7 (audio download speed) merged at round 5 with 10 criteria passed; PR #8 (mobile transcription speed and chunk boundaries) merged at round 5 with 12 criteria passed; all ended with 0 remaining P2

## Preferences

- User wants sync to rely only on Google account linking: signing in to the same account on PC and mobile should make new translations appear automatically in the other device's local storage, with no server ('서버 사용을 안하는거지')
- User does not want to deploy GCP or a server for this ('굳이 gcp나 서버를 배포해야할까? 더 우아한 방법을 마련해줘')

## Open

- Sync across different networks (e.g. a phone on mobile data and a home PC) is out of scope and unresolved
- Android background sync remains subject to OS execution restrictions
