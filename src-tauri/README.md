# Backend (`src-tauri`)

The Rust side of the app, as designed in `docs/design/backend.md` and `docs/design/api.yaml`.

| File | What it does |
| --- | --- |
| `src/updates.rs` | Anonymous approved GitHub release selection, bounded/coalesced checks, atomic dismissal high-water mark, and exact platform download validation. Native lifecycle hooks and video-site prompts are in `app.rs`; local screens use `src/ui/Updates.svelte`. See `../docs/releases/procedure.md`. |
| `src/library_store.rs`, `src/library_api.rs` | Device-local library and manual playlists (P10/P11), additive SQLite tables, ordered memberships, and confirmed deletion with durable retry markers. Existing completed translations are read in place. Only local app screens may mutate the library. |
| `src/commands.rs` | Tauri commands P1-P11 and the ACL. `capabilities/main.json` gives the app's own screen every command. `capabilities/overlay.json` gives site pages only P6-P8. |
| `src/api.rs` | What each command does: the YouTube sign-in gate, key masking, job creation rules (reuse, 409, 422, 428), progress and subtitles, and P9 (what P1 last opened, with that page's job, kept in SQLite). |
| `src/web.rs`, `src/bin/vto-web.rs` | The screens and the commands over HTTP on one port, for a browser: `PORT` and `APP_DATA_DIR` (`scripts/live.mjs` builds and starts it). 127.0.0.1 only; a request must name this server in `Host` and come from no other origin. Its key is in Credential Manager under a name tied to its data folder. The site a person opens plays on the first screen itself (a media file in a `<video>`, YouTube in its embed); with the `whisper` feature (libclang) it has the on-device model, without it a job stops at writing. With `--stand-ins` (what the adapter's `live_cmd` runs, for screenshots) Gemini, YouTube's audio and the model are replaced the way the contract host replaces them: a local Gemini that takes any key of the right shape and translates three fixed lines, a generated 13-second lecture WAV for every YouTube video, a model that writes one line per stretch of speech, and a key file in the data folder. With them, `e2e/seed.json` leaves a saved key and a ready video with three timed cues. Never use it for real work. |
| `src/pipeline.rs` | The background worker. It runs one job at a time: download, then write on the device, then translate, then notify. It records every step in SQLite, so a killed process resumes from the last written region. |
| `src/audio.rs` | Decoding to 16 kHz mono (WAV here; everything else through `src/decode.rs` on every OS, with Media Foundation only as a fallback on Windows for what it cannot open; at most six hours of output, and sample rates of 4-384 kHz, whatever a file's header or timestamps claim; a WAV whose data ends before its stated size fails, a stream's with size 0 or 0xFFFFFFFF is read to its end) and the voice-activity regions the model is given (three times the noise floor, with a lower bound that comes down with a quiet recording's loudest frames, so quiet speech is still found and a steady hum or digital silence is not). Cue times are always on the source timeline. |
| `src/decode.rs` | Decoding on every OS: symphonia for MP4/M4A, ADTS AAC, MP3 and WebM (Opus through libopus, built from source by cmake for the target; Vorbis), plus a small MPEG-TS demuxer for HLS `.ts` segments. Audio is placed by its timestamps on the timeline players use (TS: from the earliest PTS of any stream; MP4: the audio track's edit list played through, delays, cuts, skips and repeats alike, at rate 1, and in a fragmented MP4 each fragment at its own `tfdt`, so a gap between fragments stays a gap; HLS with `EXT-X-DISCONTINUITY` or a changed `EXT-X-MAP`: each section decoded on its own after its own init section, from its first timestamp, and placed where the playlist's EXTINFs put it, with an fMP4 section's audio as far after its earliest track as its first `tfdt` and edit list put it, as players line tracks up, and each of its fragments at its own `tfdt`, so a gap between fragments stays a gap; a section that does not decode fails the file rather than leave a stretch unwritten), so audio missing while the video runs on stays silence and later speech keeps its time. A download is read from disk as it is decoded, never held whole: an HLS section is read in place, its init section first, and MPEG-TS takes two passes, one to plan where each audio run goes and one to hand only the audio bytes to the decoder, so hours of video in a variant cost no memory (`tests/decode_memory.rs` measures it). Its tests run on Windows against Media Foundation. |
| `src/media.rs` | Media URL policy (http/https only; no loopback or private addresses, checked after DNS resolution and again on every redirect hop, variant, init section and segment; a name that does not resolve is refused; every request, http or https, connects to the address that was checked, with the name kept for `Host`, SNI and the certificate, and the connected address is checked again before a response is used), HLS/DASH/DRM/live probing over the whole playlist (`EXT-X-KEY:METHOD=AES-128` with an identity key is no DRM: each piece is decrypted as it is downloaded, AES-128-CBC from the tag's IV or the segment's media sequence number, the key fetched under the same URL policy; a key that does not answer or is not 16 bytes is refused as `key_unavailable` and an init section it does not decrypt as `bad_key`; `SAMPLE-AES` or another `KEYFORMAT` is `drm`, any other method `encrypted`; relative URIs resolve against where redirects land; the first piece, the first segment and the last must answer a one-byte request, or the playlist is refused as `segment_unavailable`; every init section is checked for Common Encryption marks as a `moov` is, or the playlist is refused as `drm`; the first section's init section must list a sound track and a TS segment's PMT an audio stream, or it is refused as `not_audio`; each is read at its byte range, also from a server that ignores Range, with up to 64 MiB in front of it skipped, past which it is refused as `unverifiable`; a master's variants whose CODECS name no audio and that name no AUDIO group are passed over, and the audio taken is the one a player plays with the variant chosen: its AUDIO group's `DEFAULT=YES` rendition, else `AUTOSELECT=YES`, else the first, or the variant itself when it names no group or that rendition has no URI), protected MP4 files (`sinf`/`tenc`/`pssh` in `moov`, fetched by range when it comes after `mdat`; from a server without Range, read off one GET with up to 64 MiB skipped, past which the file is refused as `unverifiable`), encrypted WebM tracks (`ContentEncryption` under `ContentEncodings`, read from `Tracks` in the first 64 KiB or, when it is not there, the first 1 MiB; a WebM whose `Tracks` cannot be found is refused as `unverifiable`), `EXT-X-BYTERANGE`, `EXT-X-DISCONTINUITY` and init sections that change (each section's byte range, playlist time and init section saved beside the download as `<audio>.sections`; every HLS download has at least one section, so its timeline starts at the first segment as players start it), files taken only when their first bytes are a container the decoder reads (WAV, MP4/M4A, WebM, MP3, ADTS AAC, MPEG-TS; anything else is refused as `not_audio`) and, for MP4, MPEG-TS and WebM, when it lists a sound track (video-only files are refused as `not_audio` too), YouTube live and upcoming broadcasts refused even when they list audio, and the download itself. |
| `src/gemini.rs` | `gemini-3.1-flash-lite` calls. One glossary order runs first (a reply with no term list is asked for again, up to three times, and a job that gets none fails as `translate_failed` rather than translate without it; `src/pipeline.rs`), then one numbered translation target per request, with preceding speech as read-only context and no timestamps. Missing, extra or duplicate reply IDs are rejected. This file also holds pricing, cost and the 1,000 KRW per hour limit. |
| `src/store.rs`, `src/db.rs` | The SQLite schema and a small binding to the OS SQLite (`winsqlite3.dll` on Windows). |
| `src/http.rs` | Outbound HTTP through WinHTTP on Windows, and elsewhere through its own HTTP/1.1 client with rustls (ring, Mozilla's roots). Requests pinned to an address (media) use that client on Windows too, since WinHTTP cannot connect to a chosen address and still check the certificate against the name. Chunked bodies are streamed. Response heads are read within bounds (8 KiB a line, 64 KiB in all, and as many trailer fields), so no server can make it hold an endless head. Each response reports the address it really connected to. |
| `src/youtube.rs` | YouTube URL parsing and the best-effort audio extractor. |
| `src/platform.rs` | Windows Credential Manager for the key. |
| `src/android.rs` | Android: the key sealed with an Android Keystore AES-GCM key, the job's foreground service (started when 영상감지 is pressed, before the media check, since Android starts one only while the app is on screen, and a start it refuses refuses the job as `background_refused`; `specialUse` from Android 14 on, so the six-hour daily limit dataSync has from Android 15 on never stops a long lecture, with `onTimeout` stopping it in time should a limit apply anyway; with a partial wake lock, so the job goes on with the screen off) and its ongoing progress notification, and the ready notice whose tap opens the video. The Kotlin half is `gen/android/app/src/main/java/dev/vto/overlay/` (`VtoPlugin.kt`, `JobService.kt`). No page can call it: the ACL grants no plugin command. |
| `src/whisper.rs` | On-device speech (`whisper` feature, part of `app`): Android uses multilingual base q5_1, greedy decoding without temperature retries and at most four CPU threads; desktop keeps large-v3-turbo q5_0 and beam search. Model downloads have pinned SHA-256 hashes. Compute buffers are reused; language is detected once per job, and text context never carries into another job. |
| `src/app.rs` | The app (`app` feature), a library module because Android loads it as `libvto.so`; `src/main.rs` runs it on the desktop. It has the screens (S1 `/` and S2 `/preferences`, `../src/ui`, built into `../dist`), the site webview with the overlay bundle injected into every page and every frame in it (`src/overlay/page.ts`: one overlay per page, over its largest video, an iframe's included, and inside the player in full screen; `src/overlay/signin.ts`: a skip button on Google's sign-in pages, taken by itself when Google refuses an in-app sign-in, to the YouTube address P1 was given, an http one over https) (its own "site" window on the desktop, the one window on Android, where `capabilities/overlay-android.json` applies), OS notifications, and a main window that only hides while a job runs. The ready toast on Windows launches `vto-open:<job id>`, a per-user protocol registered at start, so a click opens the video at any later time, after a restart too. A running app gets the launch through single-instance; a launch that names no video to open (the app started again from its shortcut) brings back the main window, shown, restored and focused, even when it was hidden while a job ran. |
| `build.rs` | For the `app` feature only: builds the screens with `vite.config.ts`, bundles `src/overlay/inject.ts` with `vite.overlay.config.ts` and runs tauri-build. |
| `android/whisper.toolchain.cmake` | The NDK toolchain for whisper.cpp in cross builds (`.cargo/config.toml` points there). |
| `src/bin/vto-contract-host.rs` | The contract host that `contract-tests` drives. It is the real core on Tauri's mock runtime, with the stand-ins that `contract-tests/src/lib.rs` lists. |

Run the tests with the repository gate:
`npm ci --prefer-offline --no-audit --no-fund && node scripts/contract-tests.mjs artifacts/junit.xml`.
The screens have their own tests and build: `npm run test:ui` and `npm run build`.

Run the screens in a browser: `PORT=8080 APP_DATA_DIR=<folder> node scripts/live.mjs`, then open `http://127.0.0.1:8080/`. Add `--stand-ins` to see every state without a Gemini key (see `vto-web` above).

Build and run the app on Windows. This needs `npm ci` first and libclang for whisper-rs's bindgen, for example from `pip install libclang`:
`LIBCLANG_PATH=<dir with libclang.dll> cargo run --release -p video-translate-overlay --features app --bin video-translate-overlay`.
`VTO_WHISPER_MODEL=<file>` uses an existing model file instead of fetching one.
The real model has its own opt-in test:
`VTO_WHISPER_MODEL=<file> cargo test --release -p video-translate-overlay --features app --test whisper_model -- --ignored`.

## Build for Android

The project is in `gen/android` (Tauri's Android Studio project, with the Kotlin plugin and service). It needs JDK 17, the Android SDK (platform 36, build-tools 35), NDK 27, Ninja on `PATH`, `LIBCLANG_PATH` as above, `rustup target add aarch64-linux-android` (or `x86_64-linux-android` for the emulator), and the Tauri CLI 2 (`cargo install tauri-cli --version ^2`):
`cargo tauri android build --apk --target aarch64 --features app` (`--debug --target x86_64` for the emulator).
On Windows the CLI ends by symlinking `libvto.so` into `gen/android/app/src/main/jniLibs/<abi>/`, which needs developer mode. Without it, copy `target/<triple>/debug/libvto.so` and the NDK's `libc++_shared.so` there, then run `gradlew assemble<Abi>Debug -x rustBuild<Abi>Debug` in `gen/android`.
A cmake cache from another generator makes whisper.cpp fail; delete `target/<triple>/*/build/whisper-rs-sys-*` then.

## Not in this build yet

- Development testing uses the Android 14 x86_64 emulator: the key in the Keystore, foreground-service background work, on-device writing, progress and ready notices, video opening, fullscreen and subtitle repair. The ARM64 0.1.6 release APK is signed with the development key; the user confirmed that subtitles work correctly on their Galaxy S21 on 2026-11-13. S21 performance and thermals have not been measured directly in development. Production store signing and the Play Console justification for the `specialUse` service remain separate release work.
- Linux and macOS have no key store yet: the key is refused rather than written in plain text.
- On the desktop, progress shows in the window title and on the first screen; the site opens in its own "영상" window rather than under the address bar, and its overlay there has the 영상감지 button.
- In a browser (`vto-web`) the first screen plays only YouTube videos and media file addresses; other sites' videos need the app, whose webview finds their media.
- Media downloads connect directly, so a system proxy that Windows would apply is not used for them (Gemini calls still go through WinHTTP).
- The YouTube extractor is unverified against the live service. When it fails, the job is refused with `youtube_unavailable` (R20).
