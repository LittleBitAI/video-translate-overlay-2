## 답 · 2026-11-17 10:32 · unverified

I looked at the real library screen — the recorded Windows and Android phone captures from 2026-11-15 plus the browser captures at 1280 and 384 px wide, against the current screen code — and your complaints hold. The screen is one phone-shaped column of bordered boxes that was simply stretched for the PC, and the playlist's videos are the last thing on the page.

## What the screen does today

- The top bar swaps out when you enter the library. The address bar is replaced by two bordered buttons, `영상 열기` and `설정`. That `영상 열기` is only a link back to the watch screen, yet the same words label the blue button on every video row that really opens a video. Nothing marks that you are in `보관함`, so it reads as two new controls appearing.
- The arrows are bare `↑` `↓` buttons. They reorder playlists, but that meaning exists only in the screen-reader label. They have the same border and size as the playlist name. On the phone capture the `↓` wraps onto its own line, detached from its row.
- Clicking a playlist looks like nothing happened. The clicked button gets no visual selected state at all. Directly below the list a management form opens instead: rename, delete, a saved-video dropdown, a link field, a name field, a cost paragraph and an add button.
- The videos are more than a screen away. With one playlist selected, the first video row starts roughly 1,100–1,350 px from the top of the page in the captures, after that form and a search field. The list does appear; it is just off-screen.
- Video rows have no thumbnail. Each row is a title, the raw URL, a status sentence and up to five equal-weight buttons. The duration the backend already returns is not shown.
- There is no PC layout. The desktop gets the same single column with 800 px-wide text fields.

## What I would hold fixed in the redesign

- Clicking a playlist shows its videos immediately, with a visible selected state.
- Each video is a card with a 16:9 thumbnail, duration, a two-line title and the site name instead of the raw URL; clicking the card opens it.
- Management controls leave the default view.
- PC and phone get structurally different layouts, not a wrapped version of one.
- The approved charcoal palette and 14/16/20/28 type scale stay — say so if you want those reopened too.
- Existing behaviour stays: named delete confirmation, no automatic translation on open, account separation, and reordering without drag gestures.

Thumbnails are feasible without backend work for YouTube only: the stored video key is the YouTube video ID, so the image address can be derived on the screen (my inference from the key format, not something built). Other sites store only a hash of the URL, so they have no image source today.

The task will also have to rewrite the library sections of `DESIGN.md`, `docs/design/frontend.md` and `README.md`, which currently describe the arrow buttons and the reveal-a-form behaviour as the design.

Five decisions change what gets built; my recommendation is first in each.

All five choices are settled, so the spec below covers the whole request in one task: the library redesign for both shapes, the edit mode, thumbnails, the shared menu on all three screens, and the documents that describe them.

Three points in it are my own calls rather than your picks:

- Drag reordering needs one small backend exception. The edit mode you picked includes a drag handle, but the backend currently accepts a move of exactly one place per request. The spec lets a move span several places in one request. Device sync sends absolute positions, so I expect it to be unaffected, and the spec makes the session confirm that. Keeping only the labeled `위로` / `아래로` buttons would avoid the backend change entirely — say so if you prefer that.
- The PC layout starts at 768 px wide, not 1024. The Windows app window in the recorded capture was 1,009 px wide, so a 1024 threshold would have given your PC the phone layout. A phone held sideways also gets the side-rail layout.
- Cards show the site name instead of the raw address. The full address moves to edit mode. The current design record says links must not hide their destination, so the record is rewritten with this change.

The session must walk the design pass in its fixed order, with padding, width and alignment answered by browser measurements rather than by eye. It must also look at the real rendering itself at phone and PC sizes, using the stand-in live server for captures.
