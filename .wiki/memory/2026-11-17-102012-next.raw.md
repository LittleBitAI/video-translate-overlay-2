## 답 · 2026-11-14 21:51 · unverified

Google-based PC–mobile synchronization is feasible. For speed, **splitting audio into “n-minute” pieces is not enough—the app already transcribes chunks of at most 30 seconds.** The next work should cover all three requests: synchronization, faster downloads, and faster mobile transcription with safe boundaries.

The app currently saves translated subtitles locally and reuses them when reopening a video. Its Google connection is YouTube sign-in; it does not synchronize the app’s library.

I recommend Google Drive’s private app-data storage for subtitles, original transcripts, video links, playlists, and—if you want seamless continuation—playback position. Both devices would keep local copies and exchange changes when connected. Google provides an app-only storage area with a narrow permission scope; authorization would be separate from YouTube login. [Google Drive documentation](https://developers.google.com/workspace/drive/api/guides/appdata)

Synchronization should exchange individual records, rather than overwrite the SQLite database. Otherwise, simultaneous changes can erase each other. Account switching, offline edits, deletion propagation, and conflicting translations need explicit handling. Syncing subtitles lets the other device reuse the translation, but the original video still needs to be accessible there.

For downloading, the current implementation has several concrete opportunities:

- The “downloading” stage includes downloading the speech model on first use. Android’s model is approximately 60 MB, separate from the video’s audio. That should have its own progress label.
- Direct files use one download stream; HLS segments download sequentially.
- A failed audio download restarts the file, potentially repeating transferred bytes.
- YouTube selection prefers AAC and then higher bitrate, rather than selecting for transcription efficiency.

These are possible contributors, not yet the established cause of your slow downloads. The performance work should separate source lookup, model preparation, audio transfer, decoding, transcription, and translation. Then it can target the actual delay—for example, resumable downloads and bounded concurrent HLS fetching while preserving segment order and existing media checks.

For transcription, the current splitter detects sound by volume, groups nearby activity, and cuts long stretches at the quietest point between roughly 20 and 30 seconds. **The quietest point is not necessarily silence or the end of a word.** Forced cuts currently have no overlapping audio, and transcription does not carry textual context between chunks.

My proposed boundary design is:

1. Prefer a sustained pause near the desired boundary, using speech detection rather than just the quietest sample. Speech detection finds pauses, not grammatical sentence endings.
2. If speech continues, use a bounded overlapping window—initially trialling about one second of shared audio. Keep the full inference window within its duration limit.
3. Reconcile the overlap using timestamps and matching words, emitting each spoken passage once. Simply clipping timestamps cannot prevent missing or repeated words.
4. Preserve every chunk’s offset on the original video timeline, and persist the boundary plan so restarting cannot change already-saved segmentation.
5. Give translation neighbouring text for sentence context while preserving the subtitle timestamps.

Upstream whisper.cpp supports speech detection, padding, and overlap, although integrating those capabilities into this app still requires work. [whisper.cpp documentation](https://github.com/ggml-org/whisper.cpp/blob/master/examples/vad-speech-segments/README.md)

This design primarily protects accuracy. Shorter chunks and overlap can add computation; running several recognizers simultaneously on a phone can also increase memory use and heat. Android already uses a smaller model, greedy decoding, and up to four threads. A further speed improvement needs actual phone measurements, not an assumed benefit from splitting.

I have left paid transcription and model downgrades out of the recommendation; neither is necessary to define the requested work. The remaining risk is promising a speed gain before identifying the dominant delay.

**No—you do not need to deploy your own server.** I made the previous proposal more operationally heavy than necessary.

I recommend **Firebase Authentication + Cloud Firestore, accessed directly by the apps**. Google operates the service; we implement synchronization inside the existing Rust/Tauri app. Firestore accepts user authentication tokens and applies access rules to those requests, so a custom API server is unnecessary for this design. [Firestore client authentication](https://firebase.google.com/docs/firestore/use-rest-api)

The proposed flow is:

1. A user signs in with Google on PC and Android.
2. Completing a translation saves it locally and uploads the synchronized records.
3. The other device detects the changes and writes them into its local SQLite library.
4. Playlists, playback position, and confirmed deletions follow the same process.
5. Offline changes wait locally and synchronize after reconnection.

Any Google account could sign in, but each account would access only its own records. Firestore’s access rules support this separation. [Firestore access rules](https://firebase.google.com/docs/firestore/security/rules-conditions)

There would still be **one-time Firebase project, Google sign-in, and access-rule configuration**. Firebase projects are Google Cloud projects underneath; this removes custom server deployment and maintenance, not all cloud setup. [Firebase project and billing model](https://firebase.google.com/docs/projects/billing/firebase-pricing-plans)

The meaningful tradeoff is background latency. While the app is open, it can monitor changes promptly. Without a server component sending push signals, I propose Android’s scheduled background work plus immediate catch-up when reopened. Periodic WorkManager jobs have a **minimum configured interval of 15 minutes**, and Android may delay execution further—that is not a promise of delivery within 15 minutes. [Android scheduling documentation](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)

For cost, the Spark plan needs no payment method. Firestore’s free database allowance includes 1 GiB of stored data, 50,000 document reads per day, and 20,000 document writes per day, shared across this project’s users—not granted separately to every Google account. I would batch subtitle records and playback updates to avoid unnecessary operations. [Firebase pricing](https://firebase.google.com/pricing), [Firestore quotas](https://firebase.google.com/docs/firestore/quotas)

Both speed improvements remain in scope, with quality preserved and targets established from the phone baseline. This proposal removes the custom server; its remaining risks are delayed background arrival and shared free-tier capacity.

## 답 · 2026-11-14 22:18 · unverified

**Yes—each user’s running PC can handle synchronization directly with their phone.** That fits your intent better than the hosted services I proposed.

Google sign-in would establish that both devices belong to the same account. The app would handle discovery and transfer separately: signing in does not itself provide the other device’s network address or a connection through its router. Google supplies verifiable account identity; peer connections still need a way to find and reach each other. [Google identity documentation](https://developers.google.com/identity/openid-connect/openid-connect), [Peer connection documentation](https://webrtc.org/getting-started/peer-connections)

For devices on the same local network, I propose:

1. Opening the PC app automatically starts its sync component.
2. The phone discovers running PC instances using local network discovery.
3. The devices authenticate the same Google account and establish an encrypted connection.
4. They exchange changed subtitles, library entries, playlists, playback position, and deletion records.
5. Each device saves the received data locally; disconnected changes wait until the next connection.

Android provides local network discovery specifically for finding services on nearby devices, including peer-to-peer file-sharing applications. A PC connected by Ethernet and a phone on Wi-Fi can participate when the network permits communication between them. [Android network discovery](https://developer.android.com/develop/connectivity/wifi/use-nsd)

This requires **no hosted synchronization database or relay** for the local-network case. Each user’s PC serves only their own connected devices. We would add a restricted sync interface, keeping the existing app commands and API keys inaccessible to peers—the current native app deliberately exposes no network command server.

The current Google connection is only YouTube login, so this needs proper app-level Google authentication rather than inspecting YouTube cookies. Google application registration remains necessary, but that is configuration, not deploying a server. [Google identity setup](https://developers.google.com/identity/openid-connect/openid-connect)

The boundary is different networks: a home PC and a phone on mobile data may not be directly reachable through their routers. Having both apps running does not remove that problem. Background synchronization also remains subject to Android’s execution restrictions.

Both speed improvements remain in scope. The smaller complete networking solution is local-network synchronization; I would not promise automatic worldwide connectivity under the same “no intermediary” constraint.
